**Follow-up #2 closed same session, pushed `fb09ecd`:** opt-in real-binary test (`tests/smoke/videoSubprocessKill.smoke.test.ts`) forces a fast deterministic timeout (env overrides, ~1ms) against real ffmpeg/whisper-cli and confirms the process is actually killed (no orphan `ffmpeg.exe`/`whisper-cli.exe`), the call rejects with a timeout error, and the temp dir stays cleanly removable (no EBUSY/EPERM from an unreleased handle). **Real bug caught while building that test:** the timeout constants in `extractFrames.ts`/`extractAudio.ts`/`transcribe.ts` were module-level `const`s evaluated once at import time — setting the override env var inside a test *after* import had zero effect. First test version silently passed at the real 120s/30s defaults without ever actually timing out (false green). Fixed by converting all three to functions read per-call (`TRM_FFMPEG_FRAME_TIMEOUT_MS`, `TRM_FFMPEG_AUDIO_TIMEOUT_MS`, `TRM_WHISPER_MIN_TIMEOUT_MS`), same pattern as `getVideoMaxBytes()` from follow-up #1. No production behavior change (env unset → same defaults). **Pattern to watch for elsewhere in this codebase:** any `const X = Number(process.env.TRM_*) || default` at module scope is untestable via env override after import — same class of bug could be lurking in other modules using that literal pattern instead of a getter function.
